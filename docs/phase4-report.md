## Architecture

- **One engine, two runners.** `packages/shared/src/schedule.ts` holds pure recurrence, time-zone/DST, holiday, assignment and SLA logic. `apps/admin-web/src/management/scheduling.ts` (`runScheduler`) uses only the Firebase web SDK, so the browser fallback and the server job (`scripts/scheduler.ts`, run with `tsx`) execute identical code under the **same security rules** as an administrator. A public frontend never impersonates a trusted scheduler, and no rule was weakened for it.
- **Idempotency.** Each occurrence is written at `tasks/occ_{scheduleId}_r{ruleVersion}_{YYYYMMDDHHmm}` inside a transaction that first checks existence. The rules reject a key whose rule version is not the schedule's current version, a paused/archived schedule, a different template version or site/location/facility/asset, and manual origin with a key.
- **Recovery and retries.** Each run plans from `max(start, generatedThrough + 1, today − 30)` to `today + 7`, so missed runs are caught up. Failures are stored on the schedule (`lastRunStatus`, `lastError`, `retryCount`) and in `schedulerRuns`; the next run retries automatically.
- **Time zones and DST.** Local wall-clock times are converted per occurrence. Non-existent times (spring forward) move forward by the gap; repeated times (fall back) use the earlier instant. Tested for Asia/Dubai and America/New_York.
- **Rule changes.** Timing edits create a new rule version effective from the first ungenerated day (or from a dragged occurrence). Not-started occurrences of the old version from that day are cancelled with a reason; started/completed work is never changed. Calendar drag offers _this occurrence_, _this and future_, or _entire schedule_.
- **Assignment.** Candidates come from one batch read per run (employees, team members, site and shift assignments, shifts, approved/taken leave, holidays) — no per-occurrence reads. Round-robin uses the deterministic rule-date sequence, so re-running an occurrence picks the same person. Least workload uses template estimated minutes of open tasks due that day. With nobody eligible, the task is created _pending_ in the unassigned queue.
- **Cases.** Work orders, complaints and escalations share a lifecycle engine (`cases.ts`); the Firestore rule functions `caseMove`, `caseReason`, `caseResponds`, `caseResolves`, … are generated from it and checked by `rules-sync.test.ts`.
- **SLA.** The most specific active policy (site + department > site > department > company) gives response and resolution targets, stored on the record when it is created. Status is derived only from those stored timestamps; breach notifications are sent by the scheduler.
- **Notifications.** IDs are `{type}_{record}_{event}_{recipient}`, so retries never duplicate. Recipients are company admins and portal users linked to employees (`employees.linkedUid`).

### Workflows

```
Work order: reported → reviewed → assigned → in_progress ⇄ on_hold → resolved → verified → closed
            reopen (reason) from resolved/verified/closed → in_progress; cancel (reason) before work starts
Complaint:  open → assigned → in_progress → resolved → closed; reopen (reason); cancel (reason); “Create work order” links once
Escalation: raised → acknowledged → in_progress → resolved → closed; reassign department (reason) → raised;
            “Escalate further” creates level n+1 once
```

## Data model and security

See [Phase 4 schema](database/phase4-schema.md). Summary of the rules:

- Every new collection is limited to active owner/admin members of an active company; no deletes; no cross-company access.
- Scheduler run updates may change only run fields; admin edits bump the revision and at most one rule version.
- Case updates need a matching numbered event in the same write and follow the generated transition table; first response, resolution and closing times must equal `request.time`.
- Notifications are readable only by their recipient, who can only set `readAt` once.
- Staff (non-admin) still have no portal access; staff are **not** made admins to work around it (Phase 5).

## Costs and paid-service notes (for decision only; nothing enabled)

- **Automatic scheduling** works on Spark through GitHub Actions (free minutes for this repository’s plan; each run takes about a minute). A Blaze-based alternative is a scheduled Cloud Function using the Admin SDK; that needs Blaze and Cloud Scheduler (small monthly cost) and is the stronger long-term option because it does not depend on a user account.
- **Photo/file evidence** needs Cloud Storage → Blaze (pay-as-you-go storage and egress) plus Storage security rules and size/type limits.
- **Email** needs a provider (for example a transactional email API) called from trusted server code; **push** needs FCM with the mobile apps (Phase 6).

## Limitations

- The manual fallback uses the signed-in admin's session and only runs while that page is open; it is a fallback, not automation.
- The scheduler account is a company admin by necessity on Spark; keep its password in GitHub secrets only, use it for nothing else, and remove its membership to disable the job.
- Calendar queries load at most 800 tasks per visible period; filters are applied in the browser after one query (no per-item reads).
- SLA targets are computed in the browser at creation from the active policy and the creation time; they are stored, not recomputed. A trusted backend would be needed for tamper-proof SLA clocks.
- Staff/technician execution remains blocked until scoped staff access (Phase 5).
